- EP mapping (src/backends/onnx.js): `webnn` → `{name:'webnn', deviceType:'cpu'}` (NOTE: plain 'webnn' = CPU in 4.3.1), `webnn-npu` → deviceType 'npu', `webnn-gpu` → 'gpu', `webnn-cpu` → 'cpu'; `webgpu` → 'webgpu'; `wasm` → 'wasm'; `auto` → all supported devices in order [webnn-npu, webnn-gpu, webnn-cpu, webnn, webgpu, wasm] (only pushed when `'ml' in navigator` / `'gpu' in navigator`); `gpu` → filter [webgpu, cuda, dml, webnn-gpu]. Unsupported device → throws `Unsupported device: "x". Should be one of: ...`.
- ORT Web WebNN EP options (https://onnxruntime.ai/docs/tutorials/web/ep-webnn.html, read 16 Oct 2026): `deviceType: 'cpu'|'gpu'|'npu'` (default 'cpu'), `powerPreference: 'default'|'low-power'|'high-performance'` (default 'default'), `context: MLContext` (pre-created; other options ignored). Page says WebNN is "available in latest versions of Chrome and Edge on Windows, Linux, macOS, Android and ChromeOS behind a 'Enables WebNN API' flag".
- dtypes (src/utils/dtypes.js): `auto, fp32, fp16, q8, int8, uint8, q4, bnb4, q4f16, q2, q2f16, q1, q1f16`. Default dtype: wasm → q8; every other device → fp32 (DEFAULT_DEVICE_DTYPE_MAPPING only lists wasm). Suffixes: fp32 '', fp16 '_fp16', q8 '_quantized', q4 '_q4', q4f16 '_q4f16', int8 '_int8', uint8 '_uint8', bnb4 '_bnb4'.
- WASM files: unless `env.backends.onnx.wasm.wasmPaths` is set, 4.3.1 points at `https://cdn.jsdelivr.net/npm/onnxruntime-web@<ver>/dist/ort-wasm-simd-threaded.asyncify.{mjs,wasm}` (asyncify build; plain build only for Safari <26 without WebGPU). Sizes: asyncify .wasm 26,861,777 B (> Cloudflare's 25 MiB per-asset cap, so NOT vendored), jspi .wasm 16.8 MB, jsep .wasm 28.4 MB, plain 14.3 MB. Transformers.js itself caches the wasm binary + factory .mjs in the Cache API (src/backends/utils/cacheWasm.js) when wasmPaths is an object → offline works after first load; the service worker also runtime-caches cdn.jsdelivr.net as a second net.
- `env.useBrowserCache` defaults to true (Cache API, cache name 'transformers-cache'); `env.allowLocalModels` default true; remoteHost https://huggingface.co/.
- Feature detection in the lib: IS_WEBNN_AVAILABLE = `'ml' in navigator`; IS_WEBGPU_AVAILABLE = `'gpu' in navigator`. Note the lib does NOT probe createContext — a browser with navigator.ml but no usable backend will still list webnn devices.

## Spec / API facts (verified 16 Oct 2026, 17:48Z)
- WebNN spec (https://webmachinelearning.github.io/webnn/, editor's draft read 16 Oct 2026): `dictionary MLContextOptions { MLPowerPreference powerPreference = "default"; boolean accelerated = true; }`, `enum MLPowerPreference { "default", "high-performance", "low-power" }`; `ML.createContext(optional MLContextOptions)` and `createContext(GPUDevice)`; `[SecureContext, Exposed=(Window, Worker)] interface ML`. There is NO `deviceType` / `MLDeviceType` in the spec any more (the old demo used `createContext({deviceType:'npu'})`). The spec note still says "MLContextOptions is under active development". Status text: Candidate Recommendation Snapshot(s) dated 11 April 2024 and 22 January 2026.
- ORT Web's WebNN EP still takes `deviceType: 'cpu'|'gpu'|'npu'` (ORT docs) — so the ORT EP, not the spec, is where NPU/GPU/CPU selection lives today; Transformers.js's `webnn-npu|gpu|cpu` strings map onto that option. The demo's capability panel probes BOTH shapes (`{deviceType}` and `{powerPreference, accelerated}`) and shows each result/error text.
- Prompt API (https://developer.chrome.com/docs/ai/prompt-api, page "Last updated: August 26, 2026"): surface `LanguageModel.availability(opts)` → string, `LanguageModel.create({ monitor(m){ m.addEventListener('downloadprogress', e => e.loaded) } })`, `session.prompt()`, `session.promptStreaming()`; page header lists Chrome 138 (extensions) and Chrome 148 (intent to ship on the web) + an origin trial for sampling parameters in Chrome 148 — research.md owns the exact status wording.

## Build decisions
- Static site, no build step: index.html, styles.css, app.js (UI, feature detection, worker orchestration, benchmark board in localStorage, caches panel), inference-worker.js (Transformers.js pipelines in a module Web Worker), sw.js (service worker), _headers (COOP/COEP — NOT honoured by the publish host, see below), tab-site.json {kind: static}, manifest.webmanifest, icon.svg, samples/.
- The worker file is named `inference-worker.js` on purpose: a file named `worker.js` makes the publish capability treat the folder as a Cloudflare Worker entry module and the control plane answers HTTP 502 (bisected 16 Oct 2026, 17:57Z).
- Transformers.js 4.3.1 is imported from `https://cdn.jsdelivr.net/npm/@huggingface/transformers@4.3.1` (the README's URL, = dist/transformers.min.js, ORT bundled). A byte-identical vendored copy is kept at ../demo-vendor/transformers-4.3.1.min.js (not in the published folder). The service worker precaches that CDN URL at install and runtime-caches cdn.jsdelivr.net (ORT .mjs/.wasm) cache-first; Transformers.js also caches the ORT wasm + model files itself in 'transformers-cache'.
- Published: https://webai-playground.sites.tab.bot/ (publish-cli site.publish, slug webai-playground, target worker/static). The host does NOT send COOP/COEP (the `_headers` file is ignored) → `crossOriginIsolated` is false → ORT runs WASM single-threaded; the capability panel states this. SIMD and JSPI are available.

## Lead's fix, 16 Oct 2026 18:12Z — offline re-inference now verified
Cause: `pipeline()` requests optional files that 404 online (e.g. `Xenova/resnet-50/resolve/main/tokenizer_config.json`); a 404 is never cached, so offline the fetch threw "Failed to fetch" and the library aborted. Fix in sw.js: for huggingface.co `/resolve/` requests with no cached copy, answer a synthetic 404 instead of rejecting (cache names bumped to v6). Republished 18:10Z. Test (headless Chromium 156, published URL, `context.setOffline(true)` + reload): resnet-50 q8 loaded from cache in 0.9 s and classified cats.jpg → tiger cat 89.2 % while offline. The only failed requests offline are the optional tokenizer_config.json ones, now answered 404 by the SW.

## NPU fallback tracing + device detection (20 Oct 2026)
Maxim, 20 Oct 2026 11:38 Oslo: "when you run this demo in webnn+npu mode, can you trace fallback when npu device is not available and work happens on gpu or cpu? … also, add device availability detection - gpu, npu".

- New `webnn-trace.js` (shared by page + worker): `probeDevice()` (context → 1-conv graph → `graph.devices`), `readOptionNames()` (getter probe: which MLContextOptions members the browser reads), `instrumentWebNN()` (wraps `ML.createContext`, `MLGraphBuilder` + `build`, counts ops per graph), `createOrtLogParser()` (ORT verbose → per-op WebNN vs CPU/WASM).
- Worker: explicit chain `webnn-npu → webnn-gpu → webnn-cpu → wasm` on errors (stops on model/network errors), optional ORT verbose (`session_options.logSeverityLevel = 0`), `freeDimensionOverrides {batch_size:1,num_channels:3,height:224,width:224}` for image models on WebNN.
- Measured, headless Chrome for Testing 156.0.8078.4, Linux, `--enable-features=WebMachineLearningNeuralNetwork` (LiteRT backend, no NPU/GPU): `createContext({deviceType:'npu'})` resolves in ~1 ms, `graph.devices = ["cpu"]`; `gpu` → `["gpu","cpu"]`; the browser reads `deviceType` + `powerPreference`, ignores `accelerated`; `opSupportLimits()` 95 ops, preferred layout nhwc.
- ResNet-50 (fp32) on webnn-npu: before the overrides 2/122 nodes on WebNN, 120 on WASM (dynamic shapes), avg 444 ms; with them 122/122 on WebNN, avg 86 ms. MobileNet-v2 fp16: 102/102 on WebNN, avg ~32 ms.
- Without the WebNN flag: the chain logs 3 failures (`Unsupported device: "webnn-npu"…`) and runs on WASM.
- Unverified: Windows ML on a real NPU (expect `graph.devices` empty → "not observable", crbug.com/418031018); Edge specifics.
- Service worker shell bumped to v10 (adds `webnn-trace.js`).

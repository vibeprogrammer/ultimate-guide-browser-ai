# How WebNN device selection actually works (Oct 2026)

Maxim, 20 Oct 2026 13:02 Oslo: *"explain me how the device selection actually works when you choose web neural network. You say that web neural network specification removed explicit device selection, but I still can switch NPU and GPU and that actually works why does it work... dive deeper into source code of Transformers.js and ONNX runtime web"*

**Short answer.** The W3C spec removed `deviceType`, but Chromium did not. Chromium still has `deviceType: "cpu" | "gpu" | "npu"` in its WebIDL, with **"cpu" as the default**. It passes the value to the WebNN service, and each OS backend uses it to pick hardware. So the NPU/GPU switch works because Chromium honours a non-standard (pre-2025) option. `powerPreference`, which the spec kept, is accepted and passed along, but **no Chromium backend reads it**: it does not change the device. `accelerated` is not implemented at all.

Pinned versions (the ones the demo runs):
- Transformers.js **4.3.1** = commit `511bb61` (tag 4.3.1), which pins `onnxruntime-web` **1.31.0-dev.20260914-8d85527a0** ([package.json L61](https://github.com/huggingface/transformers.js/blob/511bb61a7c46b73e33f1af3fb308fbd1afe98c02/packages/transformers/package.json#L61))
- ONNX Runtime = commit [`8d85527`](https://github.com/microsoft/onnxruntime/blob/8d85527a010e294a26b274749f74294b2a32cec5/) (the commit in that dev version string)
- Chromium = `b9bd6ac815` (main, read 20 Oct 2026). Live tests: Chrome 156.0.8078.4 headless, Linux

## 1. Transformers.js: `"webnn-npu"` → an ORT execution-provider object

- [`src/backends/onnx.js` L30–L44](https://github.com/huggingface/transformers.js/blob/511bb61a7c46b73e33f1af3fb308fbd1afe98c02/packages/transformers/src/backends/onnx.js#L30-L44): a fixed table. `webnn` → `{ name: 'webnn', deviceType: 'cpu' }`, `'webnn-npu'` → `{ name: 'webnn', deviceType: 'npu' }`, `'webnn-gpu'` → `{ …'gpu' }`, `'webnn-cpu'` → `{ …'cpu' }`. Plain `"webnn"` therefore means **CPU**.
- [`deviceToExecutionProviders()` L156–L172](https://github.com/huggingface/transformers.js/blob/511bb61a7c46b73e33f1af3fb308fbd1afe98c02/packages/transformers/src/backends/onnx.js#L156-L172) returns that object as the execution-provider list.
- [`src/models/session.js` L42](https://github.com/huggingface/transformers.js/blob/511bb61a7c46b73e33f1af3fb308fbd1afe98c02/packages/transformers/src/models/session.js#L42) calls it, and [L79–L80](https://github.com/huggingface/transformers.js/blob/511bb61a7c46b73e33f1af3fb308fbd1afe98c02/packages/transformers/src/models/session.js#L79-L80) does `session_options.executionProviders ??= executionProviders`. A caller's own `session_options.executionProviders` wins. That is how this demo's W3C mode passes its own `MLContext`.
- Transformers.js has no `powerPreference` mapping and never calls `navigator.ml` itself.

## 2. ONNX Runtime Web: EP options → `navigator.ml.createContext(...)`

- [`js/common/lib/inference-session.ts` L371–L398](https://github.com/microsoft/onnxruntime/blob/8d85527a010e294a26b274749f74294b2a32cec5/js/common/lib/inference-session.ts#L371-L398): `WebNNContextOptions { deviceType?, numThreads?, powerPreference? }`, plus `WebNNOptionsWithMLContext { context, deviceType (required) }`. You can hand ORT a ready-made `MLContext`; its `deviceType` then only informs ORT itself.
- [`js/web/lib/wasm/wasm-core-impl.ts` L377–L392](https://github.com/microsoft/onnxruntime/blob/8d85527a010e294a26b274749f74294b2a32cec5/js/web/lib/wasm/wasm-core-impl.ts#L377-L392): for the `webnn` EP it uses `context` if given, else a `GPUDevice`, else `webnnCreateMLContext({ deviceType, powerPreference })`.
- [`js/web/lib/wasm/jsep/backend-webnn.ts` L135–L167](https://github.com/microsoft/onnxruntime/blob/8d85527a010e294a26b274749f74294b2a32cec5/js/web/lib/wasm/jsep/backend-webnn.ts#L135-L167): `createMLContext()` caches by options and calls **`navigator.ml.createContext(options)`**. This is the one call that reaches the browser.
- [`js/web/lib/wasm/session-options.ts` L85–L98](https://github.com/microsoft/onnxruntime/blob/8d85527a010e294a26b274749f74294b2a32cec5/js/web/lib/wasm/session-options.ts#L85-L98) also writes `deviceType` into the native session config. [`onnxruntime/core/session/provider_registration.cc` L256–L259](https://github.com/microsoft/onnxruntime/blob/8d85527a010e294a26b274749f74294b2a32cec5/onnxruntime/core/session/provider_registration.cc#L256-L259) defaults it to **"cpu"**. [`webnn_execution_provider.cc` L36–L40](https://github.com/microsoft/onnxruntime/blob/8d85527a010e294a26b274749f74294b2a32cec5/onnxruntime/core/providers/webnn/webnn_execution_provider.cc#L36-L40) uses it as `wnn_device_type_` for ORT's own op-support and layout decisions, and takes the `MLContext` from `currentContext`.
- Nodes the WebNN EP rejects run on ORT's CPU (WASM) EP. That is the per-op fallback the demo's verbose trace shows.

## 3. Chromium: where `deviceType` goes

- **Blink IDL** [`ml_context_options.idl` L9–L31](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:third_party/blink/renderer/modules/ml/ml_context_options.idl;l=9): `enum MLDeviceType { "cpu", "gpu", "npu" }` and `dictionary MLContextOptions { MLDeviceType deviceType = "cpu"; MLPowerPreference powerPreference = "default"; }`. There is no runtime flag on it, no deprecation warning, and no `accelerated` member. Tested: Chrome 156 reads `deviceType` and `powerPreference` and ignores `accelerated`.
- **Blink → service** [`ml.cc` L288–L291](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:third_party/blink/renderer/modules/ml/ml.cc;l=288) (and the in-process path [L366–L369](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:third_party/blink/renderer/modules/ml/ml.cc;l=366)) send `CreateContextOptions(device, power_preference)` over Mojo ([`webnn_context_provider.mojom` L17–L31](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/public/mojom/webnn_context_provider.mojom;l=17)).
- **Backend choice** [`webnn_context_provider_impl.cc`](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/webnn_context_provider_impl.cc;l=469): Windows → ONNX Runtime / Windows ML ([L471–L497](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/webnn_context_provider_impl.cc;l=471)); macOS → Core ML ([L499–L548](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/webnn_context_provider_impl.cc;l=499)); everything else → TFLite/LiteRT ([L551](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/webnn_context_provider_impl.cc;l=551)). With LiteRT, cpu and npu requests go to the in-renderer LiteRT context ([`ShouldUseInProcessTflite` L149–L156](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/webnn_context_provider_impl.cc;l=149)).
- **Windows (ORT / Windows ML)**: `WebnnToOrtDeviceType(options->device)` → `SelectEpDeviceForCompiler` ([L732–L735](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/webnn_context_provider_impl.cc;l=732)) → [`environment.cc` L1026–L1035](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/ort/environment.cc;l=1026). **npu**: [`SelectEpDevicesForNpu` L386–L411](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/ort/environment.cc;l=386): first NPU EP device; **if there is no NPU, or its driver is blocked → `SelectEpDevicesForGpu`**. **gpu**: [L247–L259](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/ort/environment.cc;l=247): first GPU; **none or a software GPU → `SelectEpDevicesForCpu`**. Every choice also appends the CPU EP for unsupported ops ([L216](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/ort/environment.cc;l=216)). Hence: no error, silent fallback.
- **macOS (Core ML)** [`graph_impl_coreml.mm` L665–L683](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/coreml/graph_impl_coreml.mm;l=665): cpu → `MLComputeUnitsCPUOnly`. gpu **and** npu → `MLComputeUnitsAll` by default; the explicit `CPUAndGPU` / `CPUAndNeuralEngine` mapping sits behind the `WebNNCoreMLExplicitGPUOrNPU` feature, which is **off by default** ([features.mojom L38–L45](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/public/mojom/features.mojom;l=38), crbug 344935458). On a Mac, "NPU" and "GPU" therefore currently mean the same thing ("Core ML, pick anything"); only "CPU" differs.
- **LiteRT (ChromeOS/Android/Linux)** [`graph_impl_litert.cc` L481–L487](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:services/webnn/tflite/graph_impl_litert.cc;l=481): npu sets the LiteRT NPU accelerator flag (`TODO(crbug.com/454732289): Support NPU accelerator`); gpu sets the GPU accelerator. Measured here: npu → `graph.devices = ["cpu"]`; gpu → `["gpu","cpu"]`.
- **powerPreference**: carried in the Mojo struct, and `MLContext` stores it ([`ml_context.cc`](https://source.chromium.org/chromium/chromium/src/+/b9bd6ac815b7dc644f4219daf9b0a88b157ff0a8:third_party/blink/renderer/modules/ml/ml_context.cc;l=327)). No backend file reads it: I checked `webnn_context_provider_impl.cc`, `ort/environment.cc`, `ort/ort_session_options.cc`, `ort/context_impl_ort.cc`, `coreml/*`, `tflite/graph_impl_litert.cc`, `tflite/context_impl_litert.cc`. A GitHub code search over the chromium/chromium mirror finds `power_preference` under `services/webnn` only in the mojom (plus a fuzzer). It is **ignored for device selection**.

## 4. The spec side

- [webmachinelearning/webnn#809 "Remove MLDeviceType"](https://github.com/webmachinelearning/webnn/pull/809) by Zoltan Kis, merged **13 Feb 2025** (merge commit `9c00304`). Resolves #749; addresses #302, #350. The rationale is in the [device selection explainer](https://github.com/webmachinelearning/webnn/blob/main/device-selection-explainer.md): "Implementations, browsers, and the underlying OS may want to control the allocation of compute devices", so the app gives hints and the UA maps them to real adapters. Keeping `MLDeviceType` with better names was considered ("the approach prior to PR #809") and rejected as "more limited"; fingerprinting is listed as an open question. The explainer's examples are `powerPreference: 'low-power'` → "will likely map to an NPU or NPU+CPU", `'high-performance'` → "likely GPU", and `accelerated: true` → "GPU/NPU, CPU fallback may happen".
- The current spec (ED 10 Oct 2026) has `MLContextOptions { powerPreference = "default"; accelerated = true }` and says it "does not expose the actual device selected". Chromium adds the non-standard `MLGraph.devices`.
- **Chromium's plan:** I found no intent to deprecate, no deprecation warning and no crbug for removing `deviceType` (absence not proven). [chromestatus: WebNN](https://chromestatus.com/feature/5176273954144256) shows dev trial from 125 and an origin trial from 147; it has not shipped.

## 5. Tested in the demo (headless Chrome 156, Linux/LiteRT, no NPU, SwiftShader GPU)

| createContext options | graph.devices (1-conv probe) | MobileNet-v2 run (fp16) |
|---|---|---|
| `{deviceType:'npu'}` | cpu (silent fallback) | — |
| `{deviceType:'gpu'}` | gpu + cpu | gpu + cpu, avg 85 ms |
| `{deviceType:'cpu'}` / `{}` | cpu | — |
| `{powerPreference:'high-performance'}` | **cpu** (same as no options) | — |
| `{powerPreference:'low-power'}` | cpu | — |
| `{accelerated:true}` | cpu; `context.accelerated` not exposed | — |
| `{powerPreference:'low-power', accelerated:true}` (W3C mode, own MLContext → ORT `{context}`) | cpu | cpu, avg 82 ms |

So `powerPreference` and `accelerated` are **accepted and ignored** today: a context without `deviceType` is a CPU context in Chromium.

## What it means

- **Today:** the demo's NPU/GPU switch is Chromium's `deviceType`, a preference with silent fallback (Windows: NPU → GPU → CPU; macOS: GPU ≡ NPU ≡ "Core ML decides"; LiteRT: no NPU yet). Only `graph.devices` shows the result, and it is empty on Windows (crbug 418031018).
- **When Chromium follows the spec:** `deviceType` goes away, and hints have to carry the intent. The likely mapping, per the explainer and not implemented: low-power + accelerated ≈ NPU, high-performance ≈ GPU, accelerated:false ≈ CPU. The demo's new **"WebNN options → powerPreference (W3C spec)"** mode is ready for that. It creates the context with only the spec's options, hands it to ORT, and traces what `graph.devices` reports, so the day the hints start working, the trace shows it.
- **Unverified here:** the Windows and macOS behaviour, which is read from source only (no device to test on).

## 2-minute check on your laptop (Edge or Chrome with WebNN enabled)
1. Open https://webai.isainative.dev/ → Capabilities → **Device availability**. Compare the `WebNN GPU/NPU` rows with the `W3C powerPreference …` rows. Today the W3C rows should match "no options" (CPU), or show `[]` on Windows.
2. Backend **WebNN** → **WebNN options: deviceType** → device **NPU** → ResNet-50 or MobileNet → Classify. Watch Task Manager → Performance → NPU.
3. Switch **WebNN options: powerPreference (W3C spec)** → `low-power`, accelerated `true` → Classify again. Compare the NPU graph and the timings with step 2. If they match the CPU run, the hint was ignored.
4. Copy **04 Fallback trace** (both runs) and send it.
